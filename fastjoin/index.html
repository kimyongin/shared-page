0. 개요

패스트조인은 이벤트 스트림에서 복합 패턴을 탐지하는 CEP(Complex Event Processing) 솔루션이다. 각 패턴을 상태 머신으로 모델링하고, 정의를 DSL 텍스트로 동적 등록한다. 따라서 엔진 재배포 없이 새 패턴이 즉시 동작한다.

1. 어떤 문제를 해결해야 하는가

1.1 어떤 도메인인가

게임 백엔드는 플레이어의 행동을 끊임없이 추적해야 한다. 진행도, 미션 카운트, 보상 조건, 출석 체인 등. 한 플레이어는 동시에 수십 개의 진행 흐름을 가질 수 있고, 어떤 행동(이벤트)이 발생하면 그 행동에 영향을 받는 모든 흐름이 한 단계 진행되거나 종료된다.

이 일을 게임 서버 안에서 직접 처리하면 곧 비용이 폭증한다. 흐름 하나마다 DB 컬럼을 더하고, 트랜잭션을 걸고, 동시성 락을 잡아야 한다. 새 이벤트 종류가 생기면 게임 서버 코드를 손대야 한다. 따라서 진행 흐름 추적을 별도 시스템으로 분리하는 것이 자연스럽다. 그것이 패스트조인의 자리다.

1.2 단순 CRUD가 충분치 않은 이유

가장 흔한 시나리오는 횟수를 세거나 크기를 비교하는 단순한 조건 검사이지만, 실제 콘텐츠는 이보다 복잡한 처리 패턴을 요구한다.

  • "회복 스킬을 쓰지 않고 자쿰을 100초 내 잡으면 성공"
  • "해안가에서 돼지를 50마리 잡되, 도중에 한 번이라도 스킬을 쓰면 카운트 리셋"
  • "던전 입장 후 보스를 잡고, 그 후 5분 내 NPC와 대화하면 추가 보상"

이런 흐름은 카운트 한두 개로 표현되지 않는다. 상태가 있는 절차이고, 이를 자연스럽게 다루는 모델이 상태 머신이다.

1.3 Flink가 충분치 않은 이유

Apache Flink는 대표적인 CEP 엔진이지만, 게임 콘텐츠 시나리오에는 결정적인 한계가 있다.

Flink는 패턴마다 별도 어플리케이션을 배포해야 한다. 새 패턴을 추가하려면 새 jar를 만들어 배포하고, 그 어플리케이션은 같은 이벤트 스트림을 처음부터 다시 컨슘한다. 패턴이 수만 개면 어플리케이션도 수만 개다. 게임이 수만 개의 동적 패턴을 다뤄야 한다면 감당할 수 없다.

1.4 이벤트 스트림이 까다로운 이유

게임 이벤트는 초당 수만~수십만 건 발생할 수 있어, 게임 서버와 패스트조인 사이에 스트림 브로커(Apache Kafka 등)를 두는 비동기 모델을 쓴다. 이 모델은 처리량과 격리에는 좋지만, 본질적인 어려움 세 가지를 동반한다.

첫째

적재 지연

이벤트 발생 시각과 시스템이 처리하는 시각 사이의 지연이 균일하지 않다. 수십 ms~수분 차이가 나며, 서버 시계(Wall-Clock)로 시간을 판정하면 오판이 발생한다.

둘째

순서 섞임

여러 파티션에 분산된 이벤트는 발생 순서와 다르게 도착할 수 있다. 인과적으로 이른 이벤트가 늦게 도착해 결과가 뒤바뀔 수 있다.

셋째

전송 보장 (At Least Once)

같은 이벤트가 두 번 이상 컨슘될 수 있다. "50마리 잡으면 보상"에서 같은 처치 이벤트가 두 번 도착하면 카운트가 51로 흘러간다.

1.5 패스트조인의 해법

패스트조인은 두 층으로 해결한다.

도메인의 진행도 추적(1.1~1.3)은 CEP를 상태 머신 모델로 풀고 패턴 정의를 DSL 텍스트로 동적 등록하는 엔진으로 해결한다. CRUD보다 표현력 있게, Flink보다 동적으로, 한 번의 컨슘으로 N개 패턴을 처리한다.

이벤트 스트림의 어려움(1.4)은 엔진의 도구가 각각 해결한다.

적재 지연 → Event-Clock (2.6)
순서 섞임 → Ready Pattern (2.6)
전송 보장 → Dedup (2.6)

용어 — 등록된 한 패턴(=상태 머신 정의)을 Job이라 부른다. Job은 게임(gid) 단위로 등록·격리된다. 한 액터가 한 Job을 진행하는 상태를 Job Session이라 부르며, actor_id + job_id로 식별된다.

2. 패스트조인의 해결 방법

패스트조인은 이벤트 스트림에서 DSL로 정의된 패턴을 탐지한다. 핵심 구조는 stateful 외피인 Job Session과 stateless 변환기인 상태 머신 엔진의 분리이며, 각 개념은 아래에서 차례로 설명한다. DSL 문법은 3절에서 다룬다.

2.1 Event

엔진의 입력은 이벤트다. 게임에서 일어난 사실 하나로, 어떤 액터(주로 한 명의 플레이어)가 일으킨 것이다.

필드 설명
id멱등성 키
name이벤트 종류
actor_id액터 식별자
gid게임 식별자
sourceACTOR 또는 SYSTEM
timestamp발생 시각 (도착·컨슘 시각이 아님)
contentJSON 페이로드

SYSTEM 이벤트는 외부 시스템이 엔진에 보내는 합성 신호다. 대표적인 예가 외부 TTL 서비스가 Timeout 만료 시각에 발행하는 nudge 이벤트다(자세한 동작은 2.3, 2.6절(Event-Clock) 참고). SYSTEM 이벤트는 ACTOR 이벤트와 동일한 7개 필드 구조를 가지며, JSM의 라우팅 경로도 동일하다. 단, Event-Clock을 갱신하지 않는다.

2.2 Context

Job Session의 모든 데이터는 Context 하나로 표현된다. Context는 역할과 DSL 접근 권한이 다른 세 영역으로 나뉜다.

영역 DSL 접근 역할
meta 읽기 전용 (CONTEXT_META) 시스템 예약 영역. 엔진이 자동으로 관리하며 DSL 작성자는 읽기만 가능하다. operation의 context_path로 직접 쓸 수 없다. 현재 상태 이름·종료 여부·시간 메타·식별자 등을 보관한다. 필드 카탈로그는 3.1절 참고.
data 읽기·쓰기 (CONTEXT_DATA) DSL 작성자의 자유 영역. operation의 context_path로 값을 기록하고 operand의 value로 읽는다. 카운터·누적 합계·저장된 이벤트 필드 등 도메인 상태를 쌓는 공간이다. 사용 예는 3.1절 참고.
dedup 접근 불가 엔진 내부 자료구조. 처리된 이벤트 id를 보관해 중복 처리를 막는다. DSL operand로 접근할 수 없으며, 선언한 Dedup 모드에 따라 내부 구조가 달라진다. 상세는 3.5절 참고.

2.3 Transition

전이(Transition)는 한 상태에서 다른 상태로 이동하는 규칙이며 두 종류가 있다.

종류 발사 조건
Event 전이 지정 이름(event_name)의 이벤트가 도착해 operation의 최종 결과가 참이면 일어난다 (자세한 내용은 3.1절 참고)
Timeout 전이 기본 형태(지연 평가) — 현재 상태 진입 후 지정 시간이 지나면 일어난다 (Event-Clock 기준). 다음 이벤트 도착 시 만료 여부를 평가하며, 이벤트가 오지 않으면 트리거되지 않는다
정확한 시각 보장
  • Hook으로 외부 TTL 서비스에 만료 시각을 등록한다 (2.4절 참고)
  • TTL 서비스가 만료 시각에 source=SYSTEM nudge 이벤트를 스트림에 적재한다
  • 엔진이 수신해 Timeout 전이 여부를 평가한다

전이 평가 방식 — 이벤트 1건이 도착하면 transitions 배열을 위에서 아래로 한 번 순회한다. 각 전이마다 from이 현재 상태와 일치하고 조건이 충족되면 발사하고 현재 상태를 갱신한다. 첫 발사 후 중단할지, 갱신된 상태로 계속 순회할지는 transition_mode로 제어한다.

값 동작
FIRST_MATCH 첫 번째 전이가 발사되면 즉시 순회를 중단한다 (기본값)
CHAIN 발사 후 갱신된 상태를 기준으로 나머지 배열을 계속 순회한다. 전이를 독립적으로 선언해 재사용·조합하는 모듈화 수단이다

2.4 Hook

Hook은 전이가 일어날 때 호출되는 (command, value) 짝이다. 비동기가 기본이며, 엔진 내장 연산으로 완결되는 경우만 동기를 쓴다.

비동기가 기본이며 구현부가 외부에 있어 확장성과 운영이 유리하다. 동기 Hook은 반드시 필요한 경우에만 제한적으로 사용한다.

비동기 (기본) 동기 (조건부)
구현 위치 엔진 외부. 외부 시스템이 command를 구독·처리한다 엔진 내부. 내장 연산자로 구현된 command만 사용 가능하다
완료 방식 메시지 발행 후 즉시 반환. 외부 시스템이 처리 결과를 이벤트 스트림에 적재하면, 엔진이 그 이벤트를 수신해 다음 전이를 평가한다 완료까지 대기. 이벤트 트랜잭션(2.5)에 포함되어 원자적으로 처리된다
실패 처리 엔진이 직접 관찰하지 않음. 외부 시스템이 재시도·복구를 담당하며, 결과는 별도 이벤트로 통보한다 예외로 전파 → 복제본 폐기 → 이벤트 미처리로 간주
확장 비용 낮음. 새 command 추가 시 엔진 수정 없이 외부 핸들러만 추가한다 높음. 새 command 추가 시 엔진 내부를 수정해야 한다
적용 조건 제약 없음 (기본값) ① 내장 연산자로 완결 가능 + ② 다음 이벤트 도착 전 완료 필요

여러 Hook이 한 전이에 선언된 경우 선언 순서대로 순차 실행된다. 어떤 command를 지원하는지는 운영 시스템이 정의하며, SPEC은 (command, value) 짝의 형태만 정한다.

2.5 Transaction

Job Session은 이벤트마다 Context의 복제본을 만들어 엔진에 넘긴다. 엔진은 복제본 위에서 전이 평가·Context 갱신·동기 Hook 실행을 수행한다. 정상 완료 시 복제본을 반영(commit)하고, 예외가 던져지면 복제본을 폐기해 이전 Context를 유지한다.

종착 상태(transitions에 해당 상태를 from으로 갖는 전이가 하나도 없는 상태)에 도달하면 Job Session이 자동 종료된다. 엔진은 is_terminated = true, reason = TERMINATED를 기록한다.

2.6 스트림을 극복

스트림 브로커를 통한 이벤트 처리는 적재 지연·순서 섞임·전송 보장이라는 세 가지 어려움을 수반한다(1.4절). 아래 세 도구가 각각 대응한다.

첫째

Event-Clock

Job Session Manager 스코프에서 글로벌하게 관리하는 단조 클럭. source=ACTOR 이벤트가 도착할 때마다 Manager가 timestamp로 최댓값 갱신하며, 늦게 도착한 이벤트가 시간을 뒤로 돌리지 않는다. source=SYSTEM 이벤트는 클럭에 영향을 주지 않는다. 서버 시계(Wall-Clock)는 쓰지 않는다.

둘째

Ready Pattern

순서 섞임에 의한 인과 깨짐을 보정하는 DSL 작성자의 모델링 기법. *_READY 중간 상태에 잠시 머물며 늦게 도착한 이벤트가 결과를 뒤집을 수 있게 한다. 엔진이 자동 처리하지 않으므로 작성자가 명시적으로 적용해야 한다.

셋째

Dedup

처리한 이벤트 id를 보관해 같은 이벤트가 두 번 처리되지 않도록 막는다. 모드는 셋(NAIVE / BEST_EFFORT / STRICT)이며, 정확성과 메모리 사용량 사이의 트레이드오프를 Job마다 선택한다. 상세는 3.5절.

2.7 실행 절차

JSM Job Session Manager
JS Job Session
SM StateMachine
  1. JSM 이벤트 인입
  2. JSM Event-Clock 갱신 — source=ACTOR 이벤트의 timestamp로 글로벌 클럭 최댓값 갱신
  3. JSM Job, Job Session 조회 — event.gid+name으로 Job 목록 조회 → 각 Job의 actor_id+job_id로 Job Session 조회
  4. JSM 각 Job Session에 처리 위임 (팬아웃) (Job DSL, Job Meta, 이벤트)
    1. JS Context 로드 및 Meta 주입
    2. JS StateMachine 호출 — (DSL, Context_Copied, 이벤트) 전달
      1. SM 멱등성 검사 — 이미 처리된 이벤트 id면 스킵
      2. SM 전이 평가 — 선언 순 첫 매칭
      3. SM 전이 실행 · Hook 발행
      4. SM 종료 판정 — 종착 상태 도달 시 is_terminated = true, reason = TERMINATED
    3. JS Context 저장 — 정상 완료 시 커밋, 예외 시 복제본 폐기 (2.5절)
  5. JSM 처리 결과 반환

이 절차는 순서 섞임에 의한 인과 깨짐을 자동으로 풀지 않는다. 인과가 중요한 종료 판정에는 Ready Pattern을 작성자가 명시적으로 적용해야 한다.

2.8 외부 종료 요청

외부 시스템은 이벤트 스트림과 별개의 직접 API 호출로 JSM에 종료를 요청한다. 이 경로는 2.7의 이벤트 처리 흐름을 거치지 않는다. JSM은 요청에 담긴 종료 사유를 context.meta.reason에 기록하고, context.meta.is_terminated = true를 설정한 뒤 Job Session을 종료한다. 어떤 사유들이 외부에서 발행될 수 있는지(예: 세션 만료, 액터 명시 취소, 관리자 강제 종료)는 운영 결정으로 5절 "범위 밖"에 해당한다.

3. 패스트조인 DSL 살펴보기

2절의 각 개념이 DSL에서 어떻게 표현되는지 살펴본다. 시나리오는 하나다: "상급 등급(arcane_realm 또는 divine_realm) 던전에 입장해 보스를 30회 누적 처치하면 성공, 10분 안에 못 끝내면 실패." 연산자 카탈로그와 조합 패턴은 4절에서 다룬다.

아래 YAML이 이 시나리오의 전체 DSL이다. ①②③은 위 다이어그램의 전이 번호이며, 각 블록이 색상으로 구분된다.

initial_state: outer_dungeon transition_mode: FIRST_MATCH transitions:
# ① outer_dungeon → inner_dungeon (Event 전이, filter 중위식) - type: event from: outer_dungeon to: inner_dungeon value: event_name: dungeon_enter filter: expression: "A && (B || C)" items: A: operator: EQUAL operands: - { source: EVENT_CONTENT, value: $.tier } - { source: CONSTANT, value: advanced } B: operator: EQUAL operands: - { source: EVENT_CONTENT, value: $.dungeon_name } - { source: CONSTANT, value: arcane_realm } C: operator: EQUAL operands: - { source: EVENT_CONTENT, value: $.dungeon_name } - { source: CONSTANT, value: divine_realm }
# ② inner_dungeon → success (Event 전이, operation 파이프) - type: event from: inner_dungeon to: success value: event_name: boss_kill operation: expression: "A | B" items: A: operator: ADD context_path: $.aggregation operands: - { source: CONTEXT_DATA, value: $.aggregation, default_value: 0 } - { source: CONSTANT, value: 1 } B: operator: GREATER_THAN_OR_EQUAL operands: - { source: CONTEXT_DATA, value: $.aggregation } - { source: CONSTANT, value: 30 } hooks: - command: notification_send value: { message: boss_kill_success }
# ③ inner_dungeon → fail (Timeout 전이) - type: timeout from: inner_dungeon to: fail value: 600000
deduplication: mode: STRICT max_size: 10000

3.1 Event 전이

Event 전이는 filter와 operation으로 구성된다. 둘 모두 연산자(operator)로 피연산자(operands)를 처리하며, 그 결과를 context_path에 기록하거나 비교해 전이를 결정한다.

연산 구성 요소

operator 무엇을 할지

  • 사칙 — ADD, …
  • Context 쓰기 — PROJECTION, …
  • 일시·타입·컬렉션 변환
전체 카탈로그는 4.1절.
operands 무엇으로 할지 각 피연산자 구조는 아래 표 참고.

filter

중위 논리식(&& / || / 괄호)으로 연산을 결합하는 boolean 게이트다. 전체 식이 참일 때 이벤트를 받아들인다. expression에 중위식을 적고, items에 각 연산을 알파벳 키로 정의한다.

①의 A && (B || C)는 "등급이 상급이고, 이름이 arcane_realm 또는 divine_realm인 경우"를 뜻한다.

operation

파이프(A | B | C)로 step을 순차 연결한다. 각 step은 중간 결과와 무관하게 왼쪽부터 실행된다.

  • 전이 조건 — 마지막 step이 비교 연산이고 그 결과가 참이면 전이. 비교가 아니면 전이되지 않는다
  • 파이프 내 가시성 — 앞 step의 context_path 쓰기는 다음 step에 즉시 보인다
  • 부수효과 — 전이 조건 불충족 시에도 중간 step이 context.data에 쓴 값은 유지된다 (2.5의 복제본에 보존됨)

②에서 A가 카운트를 1 올리고(context.data 갱신), B가 그 값이 30 이상인지 비교해 전이 여부를 결정한다. 임계값에 아직 못 미치면 올라간 카운트는 다음 이벤트에서도 유지된다.

3.2 Timeout 전이

③처럼 type: timeout을 쓰면 이벤트 입력과 무관하게 시간만으로 전이가 일어난다. value는 ms 단위이며, Event-Clock 기준 해당 상태에 들어온 후 경과 시간으로 판정한다. ③의 value: 600000은 inner_dungeon 진입 후 600초(10분)가 지나면 자동으로 fail로 전이함을 뜻한다.

기본 형태에서는 다음 이벤트가 도착할 때 Timeout 여부를 평가한다(지연 평가). 정확한 시각에 Timeout을 발동해야 한다면 Hook을 통해 외부 TTL 서비스에 만료 시각을 등록하고, TTL 서비스가 만료 시각에 source=SYSTEM nudge 이벤트를 발행하게 한다(2.3, 2.4절 참고).

3.3 Hook

②처럼 hooks 필드에 (command, value) 짝을 나열하면, 해당 전이가 일어나는 순간 순서대로 실행된다. 비동기 Hook은 메시지를 발행하고 즉시 다음으로 넘어간다. 어떤 command를 지원하는지는 운영 시스템이 정의하며, SPEC은 (command, value) 짝의 형태만 정한다.

Hook 구조

필드 타입 필수 설명
command string ✓ 외부 시스템에 보낼 명령 이름 (ASCII)
value JSON - 명령과 함께 전달할 JSON 페이로드

3.4 Ready 상태 패턴

(개념 설명은 2.6 Ready Pattern 참고.) 동일 시나리오에 Ready 패턴을 적용하면 어떻게 달라지는지 생각해 보자.

boss_kill 이벤트가 도착했을 때, 인과적으로 더 이른 사망 이벤트가 아직 오지 않았을 수 있다(순서 섞임). 이 상황에서 바로 success로 확정하면 오판이 된다. Ready 패턴을 적용하면 success_ready 중간 상태를 두고, Event-Clock 기준 일정 시간 동안 사망 이벤트가 오는지 기다린다. 그 안에 사망 이벤트가 도착하면 fail로 뒤집고, 오지 않으면 success로 확정한다.

이 모델링은 엔진이 자동으로 해 주지 않는다. "보스를 처치하면 바로 success"와 "success_ready를 거쳐 success"는 DSL 작성자가 직접 선택해야 하는 설계 결정이다.

3.5 멱등성 정책 선언

Job마다 한 번 선언한다. dedup은 엔진 내부 자료구조이며 DSL operand로 접근할 수 없다.

mode 동작 추가 파라미터
NAIVE dedup 끔 없음
STRICT 처리한 이벤트 id를 최대 max_size개까지 보관, 동일 id 무시 max_size
BEST_EFFORT 시간 윈도우 내에서 정확. tolerance 시간보다 오래된 이벤트는 자동으로 잊힌다. max_size 초과 시 가장 오래된 항목부터 자동 제거(예외 없음). max_size · tolerance(ms) · time_truncate_millis

위 YAML의 deduplication 블록이 STRICT 예시다. 모드별 context.dedup 내부 구조는 다음과 같다.

// STRICT 모드 — 처리한 이벤트 id를 플랫 맵으로 보관
{
  "meta":  { "..생략.." },
  "data":  { "..생략.." },
  "dedup": { "evt-a1b2": true, "evt-c3d4": true, "evt-e5f6": true }
}

// BEST_EFFORT 모드 — 타임스탬프 버킷별로 묶어 보관, tolerance 초과분은 자동 제거
{
  "meta":  { "..생략.." },
  "data":  { "..생략.." },
  "dedup": {
    "1000000": { "evt-a1b2": true, "evt-c3d4": true },
    "1001000": { "evt-e5f6": true }
  }
}

4. 연산자 카탈로그와 조합 패턴

3절의 DSL 골격 안에서 실제로 쓰는 operator 종류와, 그것들을 묶어 만드는 대표 패턴을 정리한다.

4.1 연산자 카탈로그

반환 형태가 Boolean 인지 값 인지가 핵심 구분이다. 비교 연산자는 filter의 단위 항목이나 operation 파이프의 마지막 step으로 쓰이고, 변환 연산자의 결과는 context_path로 Context에 기록된다.

비교 Boolean
filter 항목 또는 operation 파이프 마지막 step
EQUALNOT_EQUAL GREATER_THANGREATER_THAN_OR_EQUAL LESS_THANLESS_THAN_OR_EQUAL INNOT_IN

AND / OR / NOT은 별도 연산자가 아니라 filter expression의 중위 토큰(&& / || / 괄호)이다. operation 결합용 |도 마찬가지다. COUNT / SUM 같은 단일 누적 연산자는 없다. 누적은 아래 패턴 A처럼 ADD로 직접 구성한다.

4.2 조합 패턴

operation은 한 transition 안에서 Context 갱신과 비교를 같은 파이프에 묶을 수 있다. YAML 스니펫은 transition value 안의 operation 또는 filter 블록만 표시한다.

패턴 A — 카운트 누적 → 임계값 비교  (위 YAML ②와 같은 구조)

이벤트마다 1씩 증가시키고, 누적값이 임계값 이상이면 전이한다.

EVENT 도착 → ADD: count+1 → $.count | ≥ 30 ? → ✓ 전이 
operation:
  expression: "A | B"
  items:
    A:
      operator: ADD
      context_path: $.count
      operands:
        - { source: CONTEXT_DATA,  value: $.count, default_value: 0 }
        - { source: CONSTANT, value: 1 }
    B:
      operator: GREATER_THAN_OR_EQUAL
      operands:
        - { source: CONTEXT_DATA,  value: $.count }
        - { source: CONSTANT, value: 30 }

패턴 B — 값 누적 → 임계값 비교

이벤트의 수치 필드를 더해 Context에 쌓고 비교한다 (예: 획득 골드 누적).

EVENT.amount → ADD: total+amount → $.total_gold | ≥ 1000 ? → ✓ 전이 
operation:
  expression: "A | B"
  items:
    A:
      operator: ADD
      context_path: $.total_gold
      operands:
        - { source: CONTEXT_DATA,   value: $.total_gold, default_value: 0 }
        - { source: EVENT_CONTENT, value: $.amount }
    B:
      operator: GREATER_THAN_OR_EQUAL
      operands:
        - { source: CONTEXT_DATA,  value: $.total_gold }
        - { source: CONSTANT, value: 1000 }

패턴 C — 이벤트 필드 Context 저장 (PROJECTION)

다음 단계의 비교나 hook 출력에 쓰기 위해 이벤트 필드를 Context로 옮긴다. 마지막 step이 비교가 아니므로 이 transition은 상태를 바꾸지 않는다. 실제 전이가 필요하면 별도 transition과 조합해 쓴다.

EVENT_CONTENT.dungeon_name → PROJECTION → $.dungeon_name → ✗ 전이 안 됨 
operation:
  expression: "A"
  items:
    A:
      operator: PROJECTION
      context_path: $.dungeon_name
      operands:
        - { source: EVENT_CONTENT, value: $.dungeon_name }

패턴 D — 다중 선택을 IN으로 단순화 (filter용)

A || B || C 형태 대신 IN 하나로 정리한다.

EVENT.name → IN [arcane_realm, divine_realm, heaven_realm] → ✓ filter 통과 
filter:
  expression: "A"
  items:
    A:
      operator: IN
      operands:
        - { source: EVENT_CONTENT, value: $.dungeon_name }
        - { source: CONSTANT,      value: [arcane_realm, divine_realm, heaven_realm] }

5. 범위 밖

본 SPEC은 상태 머신 엔진 자체의 동작에 집중한다. 다음은 운영 시스템 결정으로, 별도 문서가 다룬다.

항목 설명
Job 등록·조회·갱신 APIDSL을 시스템에 어떻게 등록하는지, 누가 접근권을 갖는지.
Job Session 생성 정책DEFAULT/AUTO_PARTICIPATION 분기, AUTO_PARTICIPATION 매칭 알고리즘과 매칭 트리거. 엔진은 세션이 생성된 이후의 이벤트 처리만 책임진다.

관측·회복탄력성트레이싱, 메트릭, 서킷 브레이커, DLQ.
인증·인가누가 무엇을 등록·실행할 수 있는지.

이 결정들은 SPEC을 만족하는 한 자유롭게 선택할 수 있다.

6. 검증 기준

엔진 구현체가 본 SPEC을 만족한다고 말하려면 다음 시나리오를 시연할 수 있어야 한다. 각 시나리오는 Given/When/Then 형식으로 기술하며, 구현자는 이를 통합 테스트로 직접 옮길 수 있다.

시나리오 1 — DSL 텍스트 등록만으로 즉시 동작

Given: 실행 중인 엔진 인스턴스. 이전에 없던 새 Job DSL 텍스트.
When: DSL 텍스트를 시스템에 등록하고, 그 Job에 해당하는 이벤트를 발행한다. 엔진은 재배포되지 않는다.
Then: 해당 이벤트가 새 Job의 전이를 유발하고, Job Session 상태가 DSL 정의에 따라 전이된다.

동적 등록

시나리오 2 — At Least Once에서도 정확한 카운트

Given: mode: STRICT 또는 BEST_EFFORT를 선언한 Job. 초기 상태에서 시작한 Job Session.
When: 동일 id를 가진 이벤트가 두 번 도착한다(재전송 시뮬레이션).
Then: context.data의 카운터는 한 번만 증가한다. 두 번째 도착한 이벤트는 dedup에 의해 무시된다.

Dedup 2.6

시나리오 3 — Event-Clock의 시간 정확성

Given: Timeout이 100초인 상태를 가진 Job. 그 상태에 진입한 Job Session. Event-Clock 기준 시작 시각 = T.
When (A): 발생 시각 T+99초인 source=ACTOR 이벤트가 도착한다(Wall-Clock 기준 도착 시각은 무관).
Then (A): Timeout 전이가 발사되지 않는다. Job Session은 이전 상태를 유지한다.
When (B): 이어서 발생 시각 T+101초인 source=ACTOR 이벤트가 도착한다.
Then (B): Timeout 전이가 발사된다. Job Session이 지정된 다음 상태로 전이된다.

Event-Clock 2.6

시나리오 4 — Ready 상태 패턴의 결과 뒤집기

Given: success_ready 중간 상태를 가진 Job. 해당 상태에 진입한 Job Session. 대기 시간 = W (Event-Clock 기준).
When: 인과적으로 success 이전에 일어난 fail 이벤트가 W 이내에 도착한다(순서 섞임으로 늦게 도착).
Then: Job Session이 success_ready에서 fail 상태로 전이된다. 종료 상태가 뒤집어진다.

Ready 패턴 2.6

시나리오 5 — 다수 Job 독립 실행 (팬아웃)

Given: 동일한 gid 안에 서로 다른 두 Job(Job-A, Job-B)이 등록되어 있고, 동일 액터에 대해 두 Job Session이 각각 존재.
When: 해당 액터의 이벤트 하나가 발행된다. 이벤트는 한 번만 컨슘된다.
Then: JSM이 gid + event.name으로 Job-A와 Job-B를 모두 조회하고, 두 Job Session에 각각 처리를 위임한다. Job-A Session과 Job-B Session은 독립적으로 전이를 평가하며, 한 Session의 상태 변화가 다른 Session에 영향을 주지 않는다.
