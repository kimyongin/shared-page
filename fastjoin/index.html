0. 개요

패스트조인은 이벤트 스트림에서 복합 패턴을 탐지하는 CEP(Complex Event Processing) 솔루션이다. 각 패턴을 상태 머신으로 모델링하고, 정의를 DSL 텍스트로 동적 등록한다. 따라서 엔진 재배포 없이 새 패턴이 즉시 동작한다.

1. 어떤 문제를 해결해야 하는가

1.1 어떤 도메인인가

게임 백엔드는 플레이어의 행동을 끊임없이 추적해야 한다. 진행도, 미션 카운트, 보상 조건, 출석 체인 등. 한 플레이어는 동시에 수십 개의 진행 흐름을 가질 수 있고, 어떤 행동(이벤트)이 발생하면 그 행동에 영향을 받는 모든 흐름이 한 단계 진행되거나 종료된다.

이 일을 게임 서버 안에서 직접 처리하면 곧 비용이 폭증한다. 흐름 하나마다 DB 컬럼을 더하고, 트랜잭션을 걸고, 동시성 락을 잡아야 한다. 새 이벤트 종류가 생기면 게임 서버 코드를 손대야 한다. 따라서 진행 흐름 추적을 별도 시스템으로 분리하는 것이 자연스럽다. 그것이 패스트조인의 자리다.

1.2 단순 CRUD가 충분치 않은 이유

가장 흔한 시나리오는 횟수를 세거나 크기를 비교하는 단순한 조건 검사이지만, 실제 콘텐츠는 이보다 복잡한 처리 패턴을 요구한다.

  • "회복 스킬을 쓰지 않고 자쿰을 100초 내 잡으면 성공"
  • "해안가에서 돼지를 50마리 잡되, 도중에 한 번이라도 스킬을 쓰면 카운트 리셋"
  • "던전 입장 후 보스를 잡고, 그 후 5분 내 NPC와 대화하면 추가 보상"

이런 흐름은 카운트 한두 개로 표현되지 않는다. 상태가 있는 절차이고, 이를 자연스럽게 다루는 모델이 상태 머신이다.

1.3 Flink가 충분치 않은 이유

Apache Flink는 대표적인 CEP 엔진이지만, 게임 콘텐츠 시나리오에는 결정적인 한계가 있다.

Flink는 패턴마다 별도 어플리케이션을 배포해야 한다. 새 패턴을 추가하려면 새 jar를 만들어 배포하고, 그 어플리케이션은 같은 이벤트 스트림을 처음부터 다시 컨슘한다. 패턴이 수만 개면 어플리케이션도 수만 개다. 게임이 수만 개의 동적 패턴을 다뤄야 한다면 감당할 수 없다.

1.4 이벤트 스트림이 까다로운 이유

게임 이벤트는 초당 수만~수십만 건 발생할 수 있어, 게임 서버와 패스트조인 사이에 스트림 브로커(Apache Kafka 등)를 두는 비동기 모델을 쓴다. 이 모델은 처리량과 격리에는 좋지만, 본질적인 어려움 세 가지를 동반한다.

첫째

적재 지연

이벤트 발생 시각과 시스템이 처리하는 시각 사이의 지연이 균일하지 않다. 수십 ms~수분 차이가 나며, 서버 시계(Wall-Clock)로 시간을 판정하면 오판이 발생한다.

둘째

순서 섞임

여러 파티션에 분산된 이벤트는 발생 순서와 다르게 도착할 수 있다. 인과적으로 이른 이벤트가 늦게 도착해 결과가 뒤바뀔 수 있다.

셋째

전송 보장 (At Least Once)

같은 이벤트가 두 번 이상 컨슘될 수 있다. "50마리 잡으면 보상"에서 같은 처치 이벤트가 두 번 도착하면 카운트가 51로 흘러간다.

1.5 패스트조인의 해법

패스트조인은 두 층으로 해결한다.

도메인의 진행도 추적(1.1~1.3)은 CEP를 상태 머신 모델로 풀고 패턴 정의를 DSL 텍스트로 동적 등록하는 엔진으로 해결한다. CRUD보다 표현력 있게, Flink보다 동적으로, 한 번의 컨슘으로 N개 패턴을 처리한다.

이벤트 스트림의 어려움(1.4)은 엔진의 도구가 각각 해결한다.

적재 지연 (1.4.1) → Event-Clock (2.5)
순서 섞임 (1.4.2) → Ready 상태 패턴 (2.8)
전송 보장 (1.4.3) → 멱등성 정책 (2.6)

용어 — 등록된 한 패턴(=상태 머신 정의)을 Job이라 부르고, 한 액터가 한 Job을 진행하는 상태를 Job Session이라 부른다.

2. 패스트조인의 해결 방법

Job Session은 내부에 상태 머신 엔진을 두고, 이벤트가 도착할 때마다 마지막 상태를 불러와 (DSL, 상태, 이벤트)를 엔진에 넘기고 결과를 새 마지막 상태로 저장한다. 엔진 자체는 stateless 변환기이고, Job Session은 stateful 외피로서 마지막 상태의 보관·영속화를 책임진다.

2.1 이벤트(Event)

엔진의 입력은 이벤트다. 게임에서 일어난 사실 하나로, 어떤 액터(주로 한 명의 플레이어)가 일으킨 것이다. 이벤트는 다섯 필드를 가진다: id(멱등성 키), name(종류), source(USER 또는 SYSTEM), timestamp(발생 시각, 도착·컨슘 시각이 아님), content(자유 페이로드).

2.2 상태(State)

상태(State)는 Job Session의 컨텍스트 데이터로, 상태 머신 엔진의 처리 결과가 갱신되어 누적된다. 시스템 meta 영역과 사용자 data 영역으로 나뉘어 관리된다.

2.3 전이(Transition)

전이(Transition)는 한 상태에서 다른 상태로 이동하는 규칙이며 두 종류가 있다: Operation 전이(이벤트와 컨텍스트에 대한 조건이 참이 되면 일어남)와 Timeout 전이(현재 상태에 들어온 후 지정된 시간이 지나면 자동으로 일어남, Event-Clock 기준). Job Session은 더 이상 전이가 일어날 수 없는 상태에 도달했을 때 종료된다.

2.4 Hook

Hook은 전이가 일어날 때 Job Session 외부의 처리를 호출하는 수단이다. (command, value) 짝을 Hook 인터페이스로 전달하면 구현체가 command를 해석해 처리한다. 주로 컨텍스트 정리·외부 시스템 호출·보상 명령 발행 등에 쓰이며, I/O가 필요한 경우 비동기 처리를 권장한다.

2.5 Event-Clock

대응: 적재 지연 (1.4.1)

Event-Clock은 Job Session 내부의 모든 시간 판정의 기준이며, 머신이 본 가장 최근 source=USER 이벤트의 timestamp 값이다. 단조 증가한다(늦게 도착한 이벤트가 시간을 뒤로 돌리지 않는다). 서버 시계(Wall-Clock)는 쓰지 않는다. 시스템 합성 신호(source=SYSTEM)는 자기 신호로 자기 시간을 정의하는 순환을 막기 위해 클럭에 영향을 주지 않는다.

2.6 멱등성 (Deduplication)

대응: 전송 보장(At Least Once) (1.4.3)

Job Session은 처리한 이벤트의 id를 보관해 같은 이벤트가 두 번 처리되지 않도록 막는다. 모드는 셋(NAIVE / BEST_EFFORT / STRICT)이며, Job마다 작성자가 정확성과 메모리 사용량 사이의 트레이드오프를 직접 선택한다. 상세 파라미터는 3.6절.

2.7 지연 허용 한도

지연 허용 한도는 엔진 차원의 운영 정책이다. 발생 후 너무 오래 묵힌 이벤트(예: 며칠 전 발생했으나 지금에야 도착한 이벤트)를 처리 자체에서 제외한다. DSL 작성자가 다루는 항목이 아니다.

주의: Ready 상태 패턴(2.8)과 다른 도구다. 지연 허용 한도는 엔진 운영 정책이고, Ready 패턴은 DSL 작성자의 모델링 기법이다.

2.8 Ready 상태 패턴

대응: 순서 섞임 (1.4.2)

Ready 상태 패턴은 순서 섞임에 의한 인과 깨짐을 보정하는 DSL 작성자의 모델링 기법이다. 종료(SUCCESS / FAIL)를 즉시 확정하지 않고 *_READY 중간 상태에 잠시 머물면서, Event-Clock 기준 대기 시간 동안 늦게 도착한 fail 이벤트가 결과를 뒤집을 수 있게 한다. 엔진이 자동으로 처리하지 않으므로, 인과 깨짐 위험이 있는 종료 판정마다 작성자가 명시적으로 적용해야 한다.

2.9 실행 절차

이벤트가 Job Session에 도착하면 다음 순서로 처리된다.

1
지연 허용 한도 검사
→
2
멱등성 검사
→
3
Event-Clock 갱신
→
4
전이 평가
→
5
전이 실행 · Hook
→
6

이 절차는 순서 섞임에 의한 인과 깨짐을 자동으로 풀지 않는다. 인과가 중요한 종료 판정에는 2.8의 Ready 상태 패턴을 작성자가 명시적으로 적용해야 한다.

3. 패스트조인 DSL 살펴보기

2절의 각 개념이 DSL에서 어떻게 표현되는지 살펴본다. 시나리오는 하나다: "상급 등급(마계 또는 신계) 던전에 입장해 보스를 30회 누적 처치하면 성공, 10분 안에 못 끝내면 실패." 연산자 카탈로그와 조합 패턴은 4절에서 다룬다.

아래 YAML이 이 시나리오의 전체 DSL이다. ①②③은 위 다이어그램의 전이 번호이며, 각 블록이 색상으로 구분된다.

initial_state: 던전외부 transitions:
# ① 던전외부 → 던전내부 (Operation 전이, filter 중위식) - type: operation from: 던전외부 to: 던전내부 value: event_name: 던전_입장 filter: expression: "A && (B || C)" items: A: operator: EQUAL operands: - { source: EVENT, type: STRING, value: $.등급 } - { source: CONSTANT, type: STRING, value: 상급 } B: operator: EQUAL operands: - { source: EVENT, type: STRING, value: $.이름 } - { source: CONSTANT, type: STRING, value: 마계 } C: operator: EQUAL operands: - { source: EVENT, type: STRING, value: $.이름 } - { source: CONSTANT, type: STRING, value: 신계 }
# ② 던전내부 → 성공 (Operation 전이, operation 파이프) - type: operation from: 던전내부 to: 성공 value: event_name: 보스_처치 operation: expression: "A | B" items: A: operator: ADD context_path: $.aggregation operands: - { source: CONTEXT, value: $.aggregation, default_value: 0 } - { source: CONSTANT, value: 1 } B: operator: GREATER_THAN_OR_EQUAL operands: - { source: CONTEXT, value: $.aggregation } - { source: CONSTANT, value: 30 } hooks: - command: 알림_전송 value: { message: 보스처치성공 }
# ③ 던전내부 → 실패 (Timeout 전이) - type: timeout from: 던전내부 to: 실패 value: 600000
deduplication: mode: STRICT max_size: 10000

3.1 상태와 전이

initial_state는 Job Session이 시작될 때의 첫 상태다. transitions는 전이 목록이며, 각 전이는 from(출발 상태)·to(도착 상태)·value(전이 조건)를 갖는다.

전이는 두 종류다. Operation 전이(type: operation)는 이벤트가 도착해 조건이 참이면 일어난다. Timeout 전이(type: timeout)는 현재 상태에 들어온 후 지정 시간이 지나면 자동으로 일어난다.

Operation 전이의 value는 event_name + filter + operation의 합성이다. event_name은 이벤트 이름으로 1차 매칭하고, filter는 이벤트 내용으로 2차 매칭한다. 한 연산의 공통 구성 요소는 세 가지다.

  • operator — 무엇을 할지. 비교(EQUAL, GREATER_THAN_OR_EQUAL, IN, …), 사칙(ADD, SUBTRACT, …), 컨텍스트 쓰기(PROJECTION, MERGE, …), 일시·타입·컬렉션 변환 등. 전체 카탈로그는 4.1절.
  • operands — 무엇을 가지고 할지. 각 피연산자는 source, type(선택), value, default_value(선택)를 가진다. source가 EVENT 또는 CONTEXT이면 value는 해당 객체에 대한 JSONPath($는 루트)이고, CONSTANT이면 value는 경로가 아니라 상수 그 자체다.
  • context_path — 결과를 어디에 둘지. 비교나 계산 결과를 컨텍스트의 이 경로에 기록한다. filter 표현식에는 없고 operation 표현식에서 쓰인다(위 YAML의 ② A 항목 참고).

3.2 표현식 — filter와 operation

filter와 operation은 결합 방식이 다르다.

filter는 중위 논리식으로 묶는다(&& / || / 괄호). expression에 중위식을 적고, items에 각 연산을 알파벳 키로 정의한다. 전체가 참일 때 이벤트를 받아들이는 boolean 게이트다. ①의 filter가 그 예다. A && (B || C)는 "등급이 상급이고, 이름이 마계 또는 신계인 경우"를 뜻한다.

operation은 파이프로 순차 연결한다(A | B | C). 각 step은 중간 결과의 참/거짓과 무관하게 왼쪽부터 순서대로 실행된다. 파이프의 마지막 step이 비교 연산이고 그 결과가 참이면 전이가 일어난다. 마지막 step이 비교가 아니면 이 transition은 전이되지 않는다. ②의 operation이 그 예다. A가 카운트를 1 올리고(컨텍스트 갱신), B가 그 값이 30 이상인지 비교해 전이 여부를 결정한다.

단일 항목이면 expression은 "A"다.

3.3 Timeout 전이

③처럼 type: timeout을 쓰면 이벤트 입력과 무관하게 시간만으로 전이가 일어난다. value는 ms 단위이며, Event-Clock 기준 해당 상태에 들어온 후 경과 시간으로 판정한다. ③의 value: 600000은 던전내부 진입 후 600초(10분)가 지나면 자동으로 실패로 전이함을 뜻한다.

3.4 Hook

②처럼 hooks 필드에 (command, value) 짝을 나열하면, 해당 전이가 일어나는 순간 순서대로 실행된다. 어떤 명령을 지원하는지(알림_전송 등)는 운영 시스템이 정의하며, SPEC은 (command, value) 짝의 형태만 정한다. I/O가 필요한 경우 비동기 처리를 권장한다.

3.5 Ready 상태 패턴

(개념 설명은 2.8절 참고.) 동일 시나리오에 Ready 패턴을 적용하면 어떻게 달라지는지 생각해 보자.

보스_처치 이벤트가 도착했을 때, 인과적으로 더 이른 사망 이벤트가 아직 오지 않았을 수 있다(순서 섞임). 이 상황에서 바로 성공으로 확정하면 오판이 된다. Ready 패턴을 적용하면 성공_READY 중간 상태를 두고, Event-Clock 기준 일정 시간 동안 사망 이벤트가 오는지 기다린다. 그 안에 사망 이벤트가 도착하면 실패로 뒤집고, 오지 않으면 성공으로 확정한다.

이 모델링은 엔진이 자동으로 해 주지 않는다. "보스를 처치하면 바로 성공"과 "성공_READY를 거쳐 성공"은 DSL 작성자가 직접 선택해야 하는 설계 결정이다.

3.6 멱등성 정책 선언

Job마다 한 번 선언한다. mode는 세 가지다.

mode 동작 추가 파라미터
NAIVE dedup 끔 없음
STRICT 처리한 이벤트 id를 최대 max_size개까지 보관, 동일 id 무시 max_size
BEST_EFFORT 정확도와 메모리 사이의 균형 조정 max_size · tolerance(ms) · time_truncate_millis

위 YAML의 deduplication 블록이 STRICT 예시다.

4. 연산자 카탈로그와 조합 패턴

3절의 DSL 골격 안에서 실제로 쓰는 operator 종류와, 그것들을 묶어 만드는 대표 패턴을 정리한다.

4.1 연산자 카탈로그

반환 형태가 Boolean 인지 값 인지가 핵심 구분이다. 비교 연산자는 filter의 단위 항목이나 operation 파이프의 마지막 step으로 쓰이고, 변환 연산자의 결과는 context_path로 컨텍스트에 기록된다.

AND / OR / NOT은 별도 연산자가 아니라 filter expression의 중위 토큰(&& / || / 괄호)이다. operation 결합용 |도 마찬가지다. COUNT / SUM 같은 단일 누적 연산자는 없다. 누적은 아래 패턴 A처럼 ADD로 직접 구성한다.

4.2 조합 패턴

operation은 한 transition 안에서 컨텍스트 갱신과 비교를 같은 파이프에 묶을 수 있다. YAML 스니펫은 transition value 안의 operation 또는 filter 블록만 표시한다.

패턴 A — 카운트 누적 → 임계값 비교  (위 YAML ②와 같은 구조)

이벤트마다 1씩 증가시키고, 누적값이 임계값 이상이면 전이한다.

EVENT 도착 → ADD: count+1 → $.count | ≥ 30 ? → ✓ 전이 
operation:
  expression: "A | B"
  items:
    A:
      operator: ADD
      context_path: $.count
      operands:
        - { source: CONTEXT,  value: $.count, default_value: 0 }
        - { source: CONSTANT, value: 1 }
    B:
      operator: GREATER_THAN_OR_EQUAL
      operands:
        - { source: CONTEXT,  value: $.count }
        - { source: CONSTANT, value: 30 }

패턴 B — 값 누적 → 임계값 비교

이벤트의 수치 필드를 더해 컨텍스트에 쌓고 비교한다 (예: 획득 골드 누적).

EVENT.amount → ADD: total+amount → $.total_gold | ≥ 1000 ? → ✓ 전이 
operation:
  expression: "A | B"
  items:
    A:
      operator: ADD
      context_path: $.total_gold
      operands:
        - { source: CONTEXT, value: $.total_gold, default_value: 0 }
        - { source: EVENT,   value: $.amount }
    B:
      operator: GREATER_THAN_OR_EQUAL
      operands:
        - { source: CONTEXT,  value: $.total_gold }
        - { source: CONSTANT, value: 1000 }

패턴 C — 이벤트 필드 컨텍스트 저장 (PROJECTION)

다음 단계의 비교나 hook 출력에 쓰기 위해 이벤트 필드를 컨텍스트로 옮긴다. 마지막 step이 비교가 아니므로 이 transition은 전이하지 않는다. 전이는 event_name + filter 조건만으로 일어나고, operation은 부수 효과(컨텍스트 갱신)만 수행한다.

EVENT.이름 → PROJECTION → $.dungeon_name → ✗ 전이 안 됨 
operation:
  expression: "A"
  items:
    A:
      operator: PROJECTION
      context_path: $.dungeon_name
      operands:
        - { source: EVENT, value: $.이름 }

패턴 D — 다중 선택을 IN으로 단순화 (filter용)

A || B || C 형태 대신 IN 하나로 정리한다.

EVENT.이름 → IN [마계, 신계, 천계] → ✓ filter 통과 
filter:
  expression: "A"
  items:
    A:
      operator: IN
      operands:
        - { source: EVENT,    value: $.이름 }
        - { source: CONSTANT, value: [마계, 신계, 천계] }

5. 범위 밖

본 SPEC은 상태 머신 엔진 자체의 동작에 집중한다. 다음은 운영 시스템 결정으로, 별도 문서가 다룬다.

  • Job 등록·조회·갱신 API — DSL을 시스템에 어떻게 등록하는지, 누가 접근권을 갖는지.
  • Job Session 라이프사이클 — 누가 Job Session을 시작·종료하는지, 외부 명시 생성과 자동 생성의 구분, 만료 정책.
  • 분산 처리 인프라 — 파티셔닝, 캐시, 영속 저장소, 컨슈머 모델, 인스턴스 간 어피니티 보장.
  • 외부 서비스 연동 — Hook의 명령 카탈로그, 외부 호출 라우팅, 결과 통지(피드백).
  • 운영 도구 — 콘솔, 플레이그라운드, 디버깅, CDC.
  • 관측·회복탄력성 — 트레이싱, 메트릭, 서킷 브레이커, DLQ.
  • 인증·인가 — 누가 무엇을 등록·실행할 수 있는지.

이 결정들은 SPEC을 만족하는 한 자유롭게 선택할 수 있다.

6. 검증 기준

엔진 구현체가 본 SPEC을 만족한다고 말하려면 다음을 시연할 수 있어야 한다.

① DSL 텍스트 등록만으로 즉시 동작

임의 패턴의 DSL을 텍스트로 등록하면 엔진 재배포 없이 바로 새 Job이 동작한다.

동적 등록

② At Least Once에서도 정확한 카운트

같은 이벤트가 두 번 도착해도 STRICT 또는 BEST_EFFORT 모드의 Job Session에서 카운트가 한 번만 증가한다.

멱등성 2.6

③ Event-Clock의 시간 정확성

Timeout이 100초인 Job Session에서, 발생 시각 99초 이벤트는 진행 상태를 유지하고 101초 이벤트는 종료 상태로 전이된다. 도착 시각이 아닌 발생 시각이 판정 기준임을 시연한다.

Event-Clock 2.5

④ 지연 허용 한도 적격성 판정

운영 정책으로 한도가 10분으로 설정된 환경에서 발생 후 11분 묵은 이벤트가 도착하면 Job Session 상태가 변하지 않는다.

지연 허용 한도 2.7

⑤ Ready 상태 패턴의 결과 뒤집기

Ready 상태에 진입한 Job Session이 ready 대기시간 안에 인과적으로 더 이른 시각의 결과 뒤집기 이벤트를 받으면 종료 상태가 뒤바뀐다.

Ready 패턴 2.8

⑥ 다수 Job 독립 실행

서로 다른 두 Job을 같은 엔진 인스턴스에 동시에 등록·실행해도 서로 독립적으로 동작한다. 한 이벤트가 양쪽 Job Session에 영향을 줄 수 있고, 이벤트는 한 번만 컨슘된다.
