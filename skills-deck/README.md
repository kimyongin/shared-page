# skills-deck

코딩 에이전트 스킬 시스템 비교용 카드 덱.

**Live**: https://kimyongin.github.io/shared-page/skills-deck/

## 목적

세 개의 유명 스킬 시스템(Matt Pocock / Superpowers / GStack)을 같은 포맷으로
나열해서, 각 시스템의 철학과 워크플로우를 한 화면에서 비교·탐색할 수 있게 한다.

원문(GitHub repo의 README, skills.md)을 그대로 옮기지 않고 *통일된 스토리 아크*로
재구성한 것이 이 덱의 핵심 가치다.

## 콘텐츠 컨셉

### 스토리 아크 — "문제 → 행동 → 결과"

각 스킬의 `tileSummary`(작은 카드)와 `heroSummary`(상세 카드)는 다음 패턴을 따른다.

> "~ 문제를 해결하기 위해 ~ 을 수행해서 ~ 렇게 해결한다."

스킬이 *무엇을 하는지*가 아니라 *무엇을 해결하는지*를 먼저 말한다.
"이 카드는 X를 한다"는 설명은 피한다.

가능하면 *구체적인 예시·인용*으로 시작한다 — \"카트 합계가 가끔 0원\", \"쿠폰 기능을
만들자\" 등. 추상적 단어로 시작하지 않는다.

### 한국어 스타일 가이드

#### 표기·표현 금기

- **\"박아\", \"때려박아\" 같은 표현 금지** — 한국어에서 어색함 (\"못 박다\" 관용구는 OK)
- **em-dash (`—`) 사용 금지** — 한국어 문서에 시각적으로 튐. 쉼표·줄바꿈·괄호로 대체
- **\"또는\" 대신 \"or\"** — 한 줄에서 분기 표현이 필요할 때
- **카테고리 개념 없음** — 모든 스킬을 단일 톤으로 통일

#### 번역체 회피

번역기가 만들어 내는 한국어 패턴을 의식적으로 피한다.

- **\"~ 위험을, ~로 막으려고\" 공식 회피** — 같은 문장 구조가 30번 반복되면 기계적
- **단편 문장 → 완전한 종결로** — \"~ 사고.\" 식 생략보다 \"~ 사고가 흔합니다.\"·
  \"~ 사고가 납니다.\"
- **한국어 어순으로 재배치** — \"X를 막기 위해 Y를 한다\"보다 \"Y를 해서 X를 막는다\"가
  자연스러운 경우가 많음
- **\"~을 풀려고\" 같은 어색한 종결 회피**

#### 어려운 한자어는 풀어 쓰기

기계 번역에서 자주 나오는 어려운 한자어는 일상어로 옮긴다.

| 피할 말 | 풀어 쓰기 |
|--------|----------|
| 비자명(非自明) | 한눈에 이유가 안 드러남 |
| 결정론적 피드백 루프 | 같은 입력이면 항상 같은 결과가 나오는 재현 환경 |
| 계측 | 계측(instrumentation)으로 풀이 병기 또는 \"로그·중단점 추가\" |
| 포스트모템 | 포스트모템(postmortem, 사후 점검 메모) |
| 편집증적 | 편집증적 (그대로 OK, 익숙한 표현) |
| 합리화 | 합리화 (그대로 OK, 단 무엇을 합리화하는지 맥락 명시) |

### 영문 약어·jargon 처리

영문 약어와 전문 용어가 등장할 때:

1. **첫 등장 시 인라인으로 풀어 적는다**
   - `<em>PMF</em>(Product-Market Fit, 제품-시장 적합성)`
   - `<em>HITL</em>(Human-in-the-loop)` / `<em>AFK</em>(Away-from-keyboard)`
   - `<em>RED</em>는 *실패하는 테스트*, <em>GREEN</em>은 *그걸 통과시키는 최소 코드*`
   - `<em>worktree</em>(같은 저장소를 별도 폴더로 떼어 낸 작업 공간)`
   - `<em>vertical slice</em>(화면→로직→DB까지 끝에서 끝까지 동작하는 작은 단위)`
   - `<em>subagent</em>(매번 새로 시작하는 보조 에이전트)`

2. **같은 카드 안에서는 두 번째 등장부터 약어만 사용**해도 OK

3. **풀이는 짧게**: 한 줄 안에 끝나도록. 정의 문서가 되지 않게

4. **풀어 쓰지 않고 그대로 두는 경우**:
   - 코드/명령(`/grill-me`, `npm install`)
   - 파일 이름(`CONTEXT.md`, `SKILL.md`, `design.md`)
   - 본문에서 *반드시 영문으로 보여야 인지되는 용어*(TDD, RED/GREEN, REFACTOR, PR, CI)

### 서사 흐름 — \"한 호흡에 이해의 곡선을 따라가게\"

문장 단위 규칙(번역체·jargon·한자어)을 모두 지켜도, 문장이 모여 만드는
*흐름*이 끊기면 결국 잘 안 읽힌다. heroSummary나 콤보 scenario처럼 여러
문장이 이어지는 곳은 **4비트 서사 구조**로 짠다.

1. **장면 설정** — *구체적 일상 경험*이나 *인용*으로 시작. 독자가
   \"아, 그 경우\"라고 즉시 인식해야 한다.
2. **원인 진단** — 왜 그 상황이 생기는지. \"오, 그래서 그랬구나\"의 반응을
   끌어낸다.
3. **메커니즘** — 이 스킬·콤보가 어떻게 그걸 뒤집는지/풀어내는지.
4. **결과의 인과** — 단순히 \"그래서 X가 됩니다\"가 아니라, *왜* X가 되는지의
   한 문장 더.

#### 흐름이 깨지는 신호

다음 패턴이 보이면 *문장 단위*가 아니라 *문단 흐름*을 손봐야 한다.

- **단편 종결** (\"~ 때.\", \"~ 모순.\") → 뒤에 뭐가 와야 할지 독자가 매달림
- **추상적 시작** (\"~ 모순이 반복될 때\") → 머릿속에 그림이 안 그려짐
- **흐름 한복판에 끼어든 정의** → 독자가 문제→해결 호흡을 잡아가는데
  갑자기 용어 풀이가 끼어듦
- **결론에서 갑자기 등장하는 새 단어** → \"잠깐, 그게 뭐?\" 멈춤
- **인과가 빠진 결과** → \"그래서 ~ 됩니다\"만 있고 *왜 그렇게 되는지*가
  없으면 독자가 빈칸을 채워야 함

#### 점검 질문

다듬을 때 자문한다:

1. 첫 문장만 읽고 \"어떤 상황인지\" 떠오르는가?
2. 둘째 문장이 첫 문장에 \"왜요?\"라고 묻는 답인가?
3. 셋째 문장이 그 답에 \"그럼 어떻게요?\"라고 묻는 답인가?
4. 마지막 문장이 \"그래서 뭐가 좋은데요?\"의 *원리적* 답인가? (단순 결과
   나열이 아니라)

> 문장 단위 규칙이 *맞춤법*이라면, 서사 흐름은 *작문력*.
> 후자가 깨지면 전자가 다 통과해도 안 읽힌다.

### 콤보 카드의 출처

콤보(combo) 시나리오는 *원문에 명시된 워크플로우만* 사용한다. 추측·합성 금지.

- **Matt**: README 본문에 명시된 워크플로우 예시 + Iron Law 인용
- **Superpowers**: 공식 7-step 워크플로우 (brainstorming → worktree → planning → ...)
- **GStack**: skills.md의 풀 라이프사이클 파이프라인 (ideation → ... → canary)

각 콤보의 `flow[].why`는 미니 카드에 표시되는 *그 시나리오 맥락에서의 의미*를 적는다.
스킬의 일반 설명을 그대로 복사하지 않는다.

#### 콤보 시나리오 작성 패턴

- 시나리오 첫 문장은 *구체적 상황 예시*로 시작 (\"테스트 파일 3개가 서로 다른 원인으로
  깨진 상황\", \"라벨이 제멋대로 붙어 있는 이슈 30개\" 등)
- 분기(or, 선택적 흐름)는 사용하지 말 것 — *순차적인 한 흐름*으로 정리
- 흐름이 가지를 쳐야 할 만큼 복잡하면 *별개의 콤보로 분리*

## 기술 컨셉

### 단일 HTML 파일

CSS·JS·데이터 모두 한 파일(`index.html`)에 인라인. 빌드 도구 없음.
GitHub Pages에 그대로 올라간다.

### JSON-driven 데이터

`DATASETS` 객체에 세 개 데이터셋(`matt` / `superpowers` / `gstack`)이 들어 있고,
렌더러는 모두 공유. 콘텐츠 수정은 데이터셋만 건드리면 끝.

각 스킬의 데이터 모델:
```js
{
  cmd, emoji, role, roleEn,
  tileSummary,    // 작은 카드 한 줄
  heroSummary,    // 상세 카드 hero 영역
  when[],         // 📌 언제 쓰나
  howCode[],      // 🎮 어떻게 쓰나 (코드 블록)
  howNote,        // (옵션) 코드 옆 설명
  what[],         // ⚡ 무엇을 하나 (블록 배열)
  output[],       // 🎁 결과물
  combos[],       // 관련 스킬 ID
  meta
}
```

### 콤보 흐름 시각화

콤보 안 미니 카드는 **번호 배지(①②③...)** 로 흐름을 표시한다.

- 화살표(→)는 사용하지 않는다 — 카드 순서·번호로 충분히 전달됨
- 텍스트 화살표(or, +, = 등)도 사용하지 않는다 — 의미는 카드 본문이 전달
- 카드 폭은 CSS Grid `auto-fit, minmax(180px, 1fr)`로 균일하게 유지
- 모바일(≤540px)은 1열로 세로 스택

### FLIP 애니메이션

작은 카드를 클릭하면 그 위치·크기에서 자라나서 모달이 된다.
`transform-origin: 0 0` + 비균등 `scale(sx, sy)` + `translate`로 계산.
(WAAPI는 초기 프레임 누락 문제로 폐기, CSS transition + reflow trick 사용)

### Markdown 내보내기

다운로드 아이콘 클릭 시 현재 데이터셋을 Markdown으로 변환해 클립보드에 복사.
`htmlToMd()`가 `<strong>` `<em>` `<code>` `<span class="pop">`을 마크다운 등가물로 변환.

콤보 화살표 규칙: 시각적으로는 화살표를 표시하지 않지만, JSON의 `arrows[]`가 남아
있으면 MD 출력에 반영됨. 새 콤보를 추가할 때는 `arrows`를 사용하지 말 것.

## 수정 가이드

### 새 스킬 추가 시

1. `DATASETS.<dataset>.skills`에 키 추가, 위 데이터 모델 그대로 채우기
2. `tileSummary`/`heroSummary`는 *문제→행동→결과* 아크로
3. 다른 스킬과 톤·길이 비슷하게 (스캔할 때 균형 깨지면 안 됨)
4. 영문 약어가 등장하면 *첫 등장 위치에서* 인라인 풀이 병기

### 새 콤보 추가 시

1. 원문에 명시적 근거가 있는지 먼저 확인. 없으면 추가하지 말 것
2. `flow[].why`는 그 콤보 맥락에서의 의미만 적기
3. 분기 흐름이면 별개 콤보로 분리. `arrows` 필드는 쓰지 말 것
4. `scenario`는 구체적 예시·상황으로 시작

### 새 데이터셋 추가 시

1. 탭에 버튼 추가 (`<button class="tab" data-dataset="<name>">`)
2. `DATASETS.<name>` 키 추가 (`preTitle`/`lead`/`footer` + `skills`/`combos`)
3. 렌더러·모달은 그대로 동작 (이미 추상화됨)

### 기존 카드 다듬기 (콘텐츠 리뷰)

기존 카드를 검토할 때 다음 순서로 본다.

1. **사실 정확도** — 원문(SKILL.md, README)을 다시 읽고 비교
   - 한국어 요약이 *원문에 없는 디테일*을 추가하지 않았는가?
   - 줄 수·단계 수·옵션 수 같은 *수치*가 정확한가?

2. **영문 jargon 점검** — 첫 등장 시 풀이가 있는가?
   - 약어(PMF, HITL, PoC, RED/GREEN, CSO 등)
   - 한국어 사용자에게 익숙하지 않은 용어(worktree, subagent, baseline)

3. **번역체 패턴 점검**
   - \"~ 위험을, ~로 막으려고\" 공식이 반복되는가?
   - 단편 문장(\"~ 사고.\")이 완전한 종결 없이 끝나는가?
   - 영어 어순을 그대로 옮긴 곳이 있는가?

4. **어려운 한자어 점검**
   - 비자명·결정론적·계측·포스트모템·정합성 게이트 등
   - 일상어로 풀거나 인라인 풀이 병기

5. **시작 문장 점검**
   - 첫 문장이 *문제 상황*을 보여 주는가?
   - *카드의 동작*을 설명하며 시작하지는 않는가?
   - 가능하면 구체적 예시·인용으로 시작하기

## 데이터 정확도 주의

- Matt의 `Engineering`/`Productivity` 분류는 *공식 README* 기준이었음
- Superpowers의 `Workflow`/`Meta` 분류는 *내가 단순화*한 것 (공식은 4개 카테고리)
- GStack의 분류도 *내가 단순화*한 것 (공식은 11+ 카테고리)

→ 현재는 카테고리 개념을 모두 제거해서 위 차이는 무관하지만, 콘텐츠 정확도를 따질
때는 이 점을 기억할 것.
